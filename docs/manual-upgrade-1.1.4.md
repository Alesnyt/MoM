# Обновление MoM до v1.1.4

Версия добавляет устойчивую очистку файлов, восстановление интерфейса после сбоев и истечения сессии, ограничения обычных запросов API, обязательные проверки перед публикацией Docker и проверку Python при запуске.

## Данные и настройки

При запуске автоматически создаётся таблица SQLite `recording_cleanup`. В неё в одной транзакции с удалением встречи записывается задание на удаление её файлов. Очистка повторяется после ошибок и перезапуска; завершение обработки этой встречи также учитывается. Очередь сохраняется вместе с базой в резервной копии. Новых томов и ручного переноса данных не требуется.

Формат встреч не меняется. Рабочие настройки остаются в `.env` без Docker или `data/config/.env` в Docker. Если обновление идёт с версии до v1.1.3, см. также [правила первоначального импорта настроек](manual-upgrade-1.1.3.md).

Очистка работает по сохранённым заданиям удаления. Файлы, оставшиеся без записи в базе ещё до обновления, автоматически не удаляются: для них требуется отдельная проверка принадлежности.

## Перед установкой

1. Дождитесь окончания обработки встреч и приостановите новые загрузки.
2. Сохраните текущий коммит и предыдущий образ/окружение для отката.
3. Создайте и проверьте резервную копию: `docker compose exec mom python -m backend.backup` или `.venv/bin/python -m backend.backup` без Docker.
4. Отдельно сохраните рабочий файл настроек с паролями и ключами. `backend.backup` его не включает.
5. Без Docker проверьте `.venv/bin/python --version`. Нужен Python **3.12+**, рекомендуется 3.12. Если окружение старее, сохраните его для отката и создайте новое через `./install.sh` с установленным Python 3.12. Установка и запуск сообщат о несовместимой версии до загрузки приложения.

## Установка

Обновите исходники до согласованного коммита PR или опубликованного тега v1.1.4. При сборке Docker из исходников:

```bash
docker compose build mom
docker compose up -d --no-deps mom
docker compose ps
docker compose logs --tail=100 mom
```

Для корпоративной установки используйте тот же файл Compose и файл окружения, с которыми она запущена, например `docker compose --env-file .env.corporate -f compose.corporate.yml ...`.

Готовый образ с тегом `v1.1.4` используйте после его публикации в GHCR. Номер исходников в PR сам по себе не означает публикацию образа. Публикация теперь ждёт успешного выполнения общего набора тестов и проверяет совпадение версии тега с версией приложения. Ручные сборки имеют тег `manual-<SHA>` и не заменяют `latest`.

Без Docker после обновления исходников выполните `./update.sh --no-pull` и перезапустите приложение, если оно запущено вручную. Общая процедура описана в [инструкции развёртывания](manual-upgrade-stage1.md).

## Проверка

- `/api/health` отвечает HTTP 200; в состояниях служб есть `recording_cleanup`.
- Старые встречи открываются, протокол скачивается; настройки каталога и почты сохранились.
- Удалённая тестовая встреча исчезла из архива, её файлы очищены. Если файловая система временно недоступна, в логе есть сообщение о повторе очистки; после устранения причины служба продолжает работу.
- После временного отключения сети архив можно загрузить повторно. Истечение сессии предлагает повторный вход; черновик новой встречи доступен после входа в тот же профиль в текущей вкладке. Обновление/закрытие вкладки не является сохранением черновика на сервере.
- Лимит аудио остаётся прежним (`MAX_UPLOAD_MB`). Обычные запросы API ограничены 1 МиБ, вход/первоначальная настройка — 16 КиБ; превышение возвращает HTTP 413, ограничение частоты входа — 429.

Реальные AD, Exchange, SMTP и модели проверяются в целевом контуре: автоматические регрессионные тесты не обращаются к корпоративным службам.

## Откат

Остановите новые загрузки и дождитесь завершения задач и очистки файлов. Верните предыдущий образ/коммит и сохранённое Python-окружение. Дополнительная таблица не требует удаления для запуска v1.1.3, но старая версия не обслуживает оставшиеся в ней задания: незавершённую очистку нужно закончить на v1.1.4.

Если требуется вернуть состояние данных до обновления, восстанавливайте согласованный снимок базы и записей вместе, а рабочий файл настроек — из отдельной копии. Не удаляйте `data/` и тома при пересоздании контейнера.
