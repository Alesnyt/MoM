# Обновление MoM до v1.1.3

Версия исправляет три проблемы, найденные при аудите: повторное использование хеша сессии, гонки при повторной обработке и удалении встреч, а также потерю файла настроек при ошибке записи в Docker. Схема SQLite и формат встреч не меняются.

## Что меняется

- Сессии проверяются и отзываются только по хешу предъявленной cookie. Хеш из базы больше нельзя использовать вместо cookie. Сессии v1.1.2 продолжают работать до своего обычного срока истечения; для очень старых сессий, сохранённых открытым текстом, потребуется повторный вход.
- Проверка состояния встречи и постановка в очередь либо удаление выполняются одной транзакцией. Конкурирующее действие, которое уже недопустимо, получает HTTP 409. Повторный запуск не возвращает работающую встречу в очередь, удаление не удаляет активную встречу.
- В Docker рабочие настройки сохраняются в `/app/data/config/.env`, на хосте — `data/config/.env`. При первом запуске новой версии они автоматически копируются из прежнего `/app/.env`. Каталог `data/` уже входит в стандартные тома; переносить настройки вручную не нужно.
- После первого запуска Docker использует `data/config/.env`. Исходный `.env` остаётся файлом первоначальной настройки и не перезаписывается. Изменения через админку сохраняются в рабочий файл и переживают пересоздание контейнера. Явные переменные окружения контейнера по-прежнему имеют приоритет над файлом.
- При запуске без Docker рабочим файлом остаётся `.env` в каталоге проекта. В обоих вариантах запись выполняется через временный файл и атомарную замену, без запасной записи поверх существующего файла.

## Перед обновлением

1. Дождитесь завершения обработки встреч и временно прекратите новые загрузки.
2. Запишите текущий коммит и сохраните предыдущий Docker-образ либо Python-окружение для отката.
3. Создайте и проверьте резервную копию базы и записей: `docker compose exec mom python -m backend.backup` или `.venv/bin/python -m backend.backup` без Docker.
4. Отдельно сохраните `.env`, а если уже существует — и `data/config/.env`, в защищённое место. Эти файлы содержат пароли и ключи и **не включаются** в снимок `backend.backup`.

Для корпоративной установки используйте тот же файл Compose, с которым она запущена: `docker compose --env-file .env.corporate -f compose.corporate.yml ...` вместо `docker compose ...`.

## Установка после объединения PR

Обновите исходники до согласованного коммита или опубликованного тега v1.1.3. Для Docker пересоберите образ и пересоздайте сервис:

```bash
docker compose build mom
docker compose up -d --no-deps mom
docker compose ps
docker compose logs --tail=100 mom
```

Если используете готовый образ, сначала загрузите его с выбранным тегом, затем пересоздайте сервис. Существующие `.env` и `data/` должны остаться на месте. Новые файлы Compose монтируют исходный `.env` только для чтения. Старый mount с правом записи также поддерживается: новая версия всё равно сохраняет настройки в `data/config/.env`.

Без Docker выполните `./update.sh --no-pull` после обновления исходников и перезапустите приложение, если оно запущено вручную. Для подробностей запуска см. [общую инструкцию обновления](manual-upgrade-stage1.md).

## Проверка после обновления

1. Откройте `/api/health`, войдите пользователем и администратором, проверьте старую встречу и скачивание протокола.
2. В админке измените тему оформления, перезапустите сервис и убедитесь, что выбор сохранился. Затем верните нужную тему. Это проверяет сохранение настроек без обращения к внешним сервисам.
3. Проверьте обработку короткой тестовой записи, остановку и повторный запуск. При конфликте действий обновите состояние встречи; HTTP 409 не означает потерю данных.
4. В Docker убедитесь, что существует `data/config/.env` с правами доступа `600`. Для ручного изменения настроек используйте этот файл, затем перезапустите сервис. Повторная правка исходного `.env` не заменяет уже созданный рабочий файл.
5. Если обновление затронуло правила каталога, повторно запустите «Синхронизировать AD». Само это обновление правила LDAP не меняет.

Приложение по-прежнему рассчитано на один worker-процесс; число параллельных встреч задаётся через `MAX_JOBS`.

## Откат и восстановление

Остановите сервис и сохраните текущие базу, записи и оба файла настроек. Верните предыдущий образ или коммит. Обратная миграция SQLite не требуется; не заменяйте текущую базу старой копией без отдельного решения о потере новых записей.

Предыдущая версия Docker читает корневой `.env`. Если после обновления настройки менялись, для их сохранения при откате используйте защищённую копию рабочего `data/config/.env` как `.env` предыдущей версии **при остановленном сервисе**. Если изменения не нужны, можно использовать сохранённый перед обновлением `.env`.

При восстановлении новой версии из снимка базы отдельно восстановите рабочий `data/config/.env` до запуска. Не публикуйте его содержимое в логах, репозитории или заявках на поддержку.
