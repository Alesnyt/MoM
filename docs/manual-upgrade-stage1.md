# Безопасное ручное обновление MoM (этап 1)

Этот релиз не меняет схему SQLite, имена переменных окружения, состав томов Docker и формат существующих записей. Новые тесты не требуют реальных LLM/ASR. Обновление в корпоративном контуре выполняется вручную после проверки PR и CI.

## Перед обновлением (на целевой ВМ)

1. Узнайте способ запуска: Docker Compose или systemd/ручной `./start.sh`. Не смешивайте способы.
2. Зафиксируйте текущий коммит: `git rev-parse HEAD`. Запишите значение на случай отката.
3. Остановите приём новых записей и дождитесь окончания уже идущих ASR/LLM-задач. Новых записей в момент обновления быть не должно.
4. Создайте резервную копию: `docker compose exec mom python -m backend.backup` (Docker) либо `.venv/bin/python -m backend.backup` (обычная установка). Проверьте вывод команды и сохраните снимок вместе с файлом `.env` в защищённом месте. Модели не входят в снимок.
5. Сохраните **рабочий Docker-образ** с предыдущей версии (`docker image save`) или убедитесь, что предыдущий git-коммит и Python-окружение доступны. Не полагайтесь на плавающий тег `:latest`.
6. Убедитесь, что есть запас диска под новый образ/зависимости и резервную копию.

## Обновление после merge PR

### Docker Compose

```bash
git fetch origin
git checkout main
git pull --ff-only
docker compose build
docker compose up -d --no-deps mom
docker compose ps
docker compose logs --tail=100 mom
```

Не выполняйте `docker compose down -v` или `docker system prune --volumes`. Важно: при первом запуске Docker Compose файл `.env` уже должен существовать — образ использует его как bind mount.

### systemd / Linux без Docker

```bash
git fetch origin
git checkout main
git pull --ff-only
./update.sh --no-pull
sudo systemctl status mom.service --no-pager
```

Для ручного запуска используйте `./start.sh` после остановки прежнего процесса. Скрипт `update.sh` не удаляет `.env` и `data/`, однако обновляет зависимости. Для гарантированного отката Python-окружения полезно сохранить его snapshot или зафиксировать версии `pip freeze`.

## Smoke test после обновления

- Открыть `/api/health`: HTTP 200, `ok: true`, `ffmpeg: true`.
- Войти существующим пользователем и администратором; проверить архив старых встреч и открыть старый протокол.
- Загрузить **короткую тестовую** запись, убедиться, что она появилась в очереди, затем в состоянии `review`, при необходимости поправить спикера и собрать протокол до `done`.
- Проверить скачивание Markdown и отображение старых результатов.
- Создать тестовую встречу в очереди и проверить остановку / запуск заново отдельно от боевых записей.
- Просмотреть журнал приложения на ошибки и проверить свободный диск.
- При возможности проверить вход второго пользователя: он не должен видеть чужие встречи.

## Откат

Если проверки не проходят: прекратить загрузки, остановить новый процесс; сохранить аварийные логи; вернуть **записанный предыдущий коммит** и старый образ (Docker) / прежнее виртуальное окружение (systemd), перезапустить сервис и повторить smoke test. Так как схема SQLite не менялась, обратная миграция базы не требуется. Не восстанавливайте старую БД поверх новой автоматически: это уничтожит записи, загруженные после обновления. Для восстановления из снимка сначала отдельно зафиксируйте текущие данные.

**Важное ограничение:** исправление остановки выполняет её кооперативно. Если ASR уже считает аудио в системном потоке, фактическое освобождение слота произойдёт после завершения выполняемой операции, чтобы новый job не гонял ту же модель одновременно.
