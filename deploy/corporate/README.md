# Развёртывание в корпоративном контуре

Это отдельная конфигурация. Обычные `Dockerfile` и `docker-compose.yml` продолжают
работать без сертификатов, корпоративного прокси и локальных пакетов.

Из корня репозитория:

1. Сохраните существующие `.env`, `data/` и `backups/`. Для новой установки скопируйте
   `.env.example` в `.env`.
2. Скопируйте `deploy/corporate/env.example` в `.env.corporate`. Укажите `SERVER_NAME`,
   HTTP(S)-прокси и префикс зеркала Docker с завершающим `/`, если они нужны.
   Выберите свободную подсеть и два адреса в ней. Не пересекайте её с сетью AD/VPN.
3. Положите сертификат сервера с цепочкой в `certs/cert.cer`, ключ без пароля —
   в `certs/cert_no_pass.key`. Ограничьте доступ к ключу. Эти файлы не входят в Git
   и не отправляются в контекст сборки.
4. Если прокси перехватывает TLS или LLM использует корпоративный CA, положите
   публичные сертификаты доверенных CA (PEM, расширение `.crt`) в
   `deploy/corporate/ca/`. Они добавляются при сборке и используются npm, pip,
   HTTPX/OpenAI, Requests и системным TLS. Закрытые ключи сюда не кладите.
5. Выполните:

   ```sh
   docker compose --env-file .env.corporate -f compose.corporate.yml config --quiet
   docker compose --env-file .env.corporate -f compose.corporate.yml up -d --build
   ```

Не объединяйте этот файл с `docker-compose.yml`: корпоративная конфигурация уже
содержит сервис приложения без опубликованного порта. Наружу доступны только
порты nginx. Перед переходом остановите старый контейнер приложения, чтобы два
экземпляра не обрабатывали одну SQLite-базу. Не удаляйте тома и каталоги данных.
Прокси для загрузки Docker-образов настраивается также в Docker daemon; build args
относятся к командам внутри сборки. Эта сборка не является полностью автономной:
npm, apt и pip должны иметь доступ к репозиториям через разрешённый прокси.

`MAX_UPLOAD_MB` задаётся в `.env.corporate` и передаётся приложению. nginx передаёт
файлы потоком, не сохраняя всё тело до авторизации. Фиксированный IP nginx —
единственный доверенный адрес прокси, помимо loopback. Входящие forwarded-заголовки
заменяются nginx. `HTTP_PORT`/`HTTPS_PORT` можно менять для проверок; для рабочего
перенаправления HTTP→HTTPS используйте стандартный HTTPS-порт 443.

## Необязательные локальные пакеты

Чистый клон собирается без `wheels`. При ограниченном доступе к PyTorch можно
поместить заранее скачанные CPU wheels в `deploy/corporate/wheels/`. Например,
на машине с интернетом для Linux x86_64, Python 3.12:

```sh
python -m pip download --only-binary=:all: --no-deps \
  --platform manylinux_2_28_x86_64 --python-version 312 --implementation cp --abi cp312 \
  --index-url https://download.pytorch.org/whl/cpu \
  torch==2.8.0 torchaudio==2.8.0 --dest deploy/corporate/wheels
```

Для ARM64 нужны соответствующие wheels. Версии закреплены в локальном
`constraints.txt`; пакеты должны совпадать с архитектурой контейнера. Не добавляйте
CUDA-пакеты для CPU-развёртывания. Пакеты и сертификаты игнорируются Git.
Диаризация включена по умолчанию в корпоративной сборке; `INSTALL_DIARIZE=0`
отключает установку её библиотек. Доступ к весам и условия Hugging Face настраиваются
отдельно, как описано в основном README.

## Области входа AD и одинаковые email

Настройки авторизации хранятся в `.env` приложения. При необходимости задайте
полные DN разрешённых областей (JSON-массив внутри одинарных кавычек):

```dotenv
LDAP_BASE_DN=DC=corp,DC=example
LDAP_AUTH_BASE_DNS='["OU=Employees,OU=Moscow,DC=corp,DC=example","OU=Employees,OU=SPB,DC=corp,DC=example"]'
```

Поиск идёт сразу внутри этих областей, а не по первым двум совпадениям во всём
каталоге. Во всех разрешённых областях должна остаться ровно одна учётка на email;
неоднозначный или неполный ответ не разрешает вход. Можно использовать `CN=Users`
как полноценный DN. Области должны находиться внутри `LDAP_BASE_DN`.
Пустое значение сохраняет прежний вход по `LDAP_BASE_DN` и `LDAP_USER_FILTER`;
`[]` и неверные DN блокируют вход с сообщением о конфигурации. После изменений
перезапустите приложение. Старый `LDAP_ALLOWED_OU` замените на полные DN.

Это отдельно от ограничения подсказок при разметке спикеров: их области по-прежнему
выбираются в админке. Никакого неявного требования `OU=Users` нет.

Проверки перед вводом в работу: HTTPS и перенаправление, вход двух пользователей,
Secure-cookie, подключение LLM с корпоративным CA, разрешённая и запрещённая
учётки AD, большой файл и отказ при загрузке без входа.
